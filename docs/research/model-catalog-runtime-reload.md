# 聚合成员能力与运行时目录重载

## 结论

修改受管 catalog 文件或刷新 renderer 模型列表，不等于正在运行的原生
app-server 已重新读取模型能力。新增聚合成员自带的上下文窗口、自动压缩阈值
同样属于后端能力变更，保存并不等于运行中的模型参数已经更新。
保存时提示可能需要重启才能正确加载这些参数，允许用户明确选择先保存、暂不重启。

代理地址、凭据和纯路由变更仍使用已有的代理热更新路径；本次不改变其判定。

## 隔离验证

使用 `codex-cli 0.162.0-alpha.17.2`，为测试进程指定全新的 `CODEX_HOME`
和 `CODEX_SQLITE_HOME`。不连接桌面客户端，不发送模型请求，不读取真实认证。

1. 用仓库模型模板生成只含 `probe-old` 的 catalog，窗口为 200000。
2. 在隔离 config 中设置绝对 `model_catalog_json`，启动独立的
   `codex app-server --listen stdio://`。
3. 初始化后调用原生 `model/list`，结果只有 `probe-old`。
4. 将同一 catalog 文件改为包含 `probe-old` 和 `probe-new`；后者窗口为
   1048576，压缩阈值为窗口的 90%。
5. 在原进程中再次调用 `model/list`，结果仍只有 `probe-old`。
6. 使用相同隔离配置启动第二个 app-server，`model/list` 才返回两个模型。

该实验直接证明当前版本没有在这条路径中重新读取本地 catalog；它不声称
测量了实际压缩触发点，也不证明未来版本或其他原生接口无法支持热重载。

上游 `codex-rs/models-manager/src/manager.rs` 的 `StaticModelsManager`
也将权威目录保存在内存中，`raw_model_catalog` 返回该内存数据，忽略刷新策略。
这是辅助源码证据；兼容性判断仍应以实际宿主版本的隔离验证为准。

## 保存交互

保存确认区分聚合成员能力变化、客户端配置变化和无法复用本地代理。仅涉及模型能力
时显示成员名称与“可能需要重启才能正确加载模型参数”，提供三个操作：

- “保存，暂不重启”：保存设置、更新目录和代理设置，保留当前客户端进程；部分模型
  参数可能暂未生效，用户可以稍后手动重启。
- “继续保存并重启”：先保存成功，再执行原有重启流程。
- “取消”或关闭对话框：不保存，也不重启。

如果同时涉及客户端连接配置、登录状态或无法复用本地代理，优先使用对应的原有
重启确认，不能被模型能力变化掩盖。不能将“列表已更新”描述为“窗口和压缩参数
已经在原生后端生效”。

要保证能力变更无需重启即可完整生效，需要实现并验证后端目录重载或等价的原生能力更新
机制，覆盖新增模型、已有会话、模型切换和压缩阈值；只放宽前端判定不足以完成。

## 模型列表完整性：原生用户配置缓存

切换聚合供应商后，可能出现目录和模型 query 原始数据都完整，但模型选择器
只显示默认成员的现象。宿主模型 observer 使用 `config/user/local` 判断是否启用
自定义目录；该配置 query 禁用自动读取，旧配置仍会使 observer 按旧名单过滤模型。
仅更新模型缓存或 invalidate 配置 query 都不足以刷新这个 disabled observer。

目录应用后，通过已有本机用户配置 query 的 `fetch` 重新调用其原生 `queryFn`，
使宿主读取磁盘配置并重建模型 query key 和过滤条件。该流程不写入配置、不调用
模型选择回调，也不重启应用；远程主机及其他配置 query 不参与。

按目录内容和配置 revision 去重，不随轮询 epoch 重读；延迟挂载的配置 query 仍能
刷新。读取失败（包括宿主返回失败兜底数据）退避重试；连续切换时，在进行中的
读取结束后再读取当前配置，避免旧完成状态吞掉更新。

在 `codex-cli 0.162.0-alpha.17.2` 对应的桌面宿主中，现场原始数据包含 12 项、
observer 与选择器仅包含 4 项；单独重新读取本机用户配置后，两者均恢复为 12 项，
当前会话、模型及推理等级保持不变。这证明该列表问题可以不重启修复；它不构成
原生后端已重新读取模型能力或已采用新压缩阈值的证据。

## 原生有效窗口的数值验证

进一步以同版本原生二进制连接本机随机端口的 Responses SSE 模拟服务，使用隔离
配置实际完成 turn，读取 `thread/tokenUsage/updated.modelContextWindow`。
仅访问本机模拟服务，不读取真实认证、不发送真实模型请求。

| 场景 | 原生报告的有效窗口 |
| --- | ---: |
| 进程启动时目录已有模型，窗口 200000、有效比例 95% | 190000 |
| 同进程将该模型文件窗口改为 400000，再创建新会话 | 190000 |
| 同进程目录新增窗口 1048576 的模型，再创建新会话 | 258400 |
| 新模型在新会话 config 中显式传入窗口 1048576、压缩阈值 943718 | 258400 |
| 已加载的新模型会话在 resume config 中传入同样覆盖值，再运行 turn | 258400 |
| 用更新后的同一目录启动全新的隔离进程：旧模型 400000 | 380000 |
| 同一全新隔离进程：新增模型 1048576 | 996147 |

新增模型可以完成调用，但伴随原生“未找到模型元数据，使用 fallback”事件。
258400 对应默认 272000 窗口的 95%，并非配置的 1M 有效窗口。已加载会话 resume
的 config 覆盖还会被原生日志明确标记为忽略。协议 schema 允许这些键，不代表
当前二进制会采用它们；上述参数覆盖不能作为已验证的新会话免重启方案。
新进程对照正确读取了文件中的两个窗口，排除了目录格式或数值观测链本身的问题；
差异来自进程内的模型元数据快照。

该实验直接测得窗口，不包含实际自动压缩触发点测量，也不能代替对具体用户会话
的观测。因此“新增模型能够调用”与“窗口、压缩参数均已生效”仍需分开判定。

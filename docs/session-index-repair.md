# 会话索引修复

管理工具 → 会话管理 → “修复会话索引”（位于“修复历史会话”右侧）。无需指定会话或记住缺失内容。操作完成后页面显示读取文件、缓存命中、恢复数量、跳过原因、耗时和备份位置。重新打开会话可读取修复后的原生消息流。

报告将正在写入、执行中和原生轮次尚未建立的项目列为“自动稍后复查”，无需立即人工处理；“需核查”只包含解析损坏或证据冲突等问题。同一轮内追加的消息按记录位置逐条核对，已存在的消息不因一轮有多条指令而误报冲突。

“启动前自动修复历史会话”开启并保存后，启动器在启动前执行检查，并在 Codex 运行期间每次检查完成后间隔 60 秒再次检查。每次读取已保存开关；关闭后停止后续自动检查。正在进行的事务会正常结束。检查失败记录诊断，不因消息修复失败阻止启动。

扫描范围包括当前 CODEX_HOME 的 sessions 和 archived_sessions。普通纯文本消息需要原始用户事件与 response_item 原文、轮次相互印证；目标消息需要目标事件与首轮内部上下文原文一致。只补回已存在且结束的原生轮次，或重新连接原文一致的孤立用户消息。恢复使用 thread_history_1.sqlite 的原生 userMessage 投影，不创建新任务、不发送新指令、不修改 rollout。

已有不同消息、混合附件、无法确认位置、未知数据库格式和正在变化的文件不会被猜测恢复。该工具不能恢复从未保存或已彻底删除的原文，也不保证修复所有形式的历史损坏。供应商和任务目录问题继续使用“修复历史会话”。

性能：按文件大小和修改时间缓存解析结果，未变化文件不重复读取正文；每次仍核对原生索引，因此原生索引重建后也能重新恢复。变化文件采用流式解析，首次检查时间取决于全部历史记录大小。缓存、最近报告和每次发生修复前的数据库备份存放在 CODEX_HOME/session-index-repair。备份可能较大，仅发生实际待修复项时创建，不会在无变化检查时生成。

# 会话索引修复

管理工具 → 会话管理 → “修复会话索引”（位于“修复历史会话”右侧）。无需指定会话或记住缺失内容。操作完成后页面显示读取文件、缓存命中、恢复数量、跳过原因、耗时和备份位置。重新打开会话可读取修复后的原生消息流。

报告先核验消息是否已存在，轮次残留 inProgress 不再把已显示消息计入等待。缺少原生轮次、暂时不允许写入、文件正在变化才列为“短暂等待”。持续等待至少 30 分钟，或消息及文件均已超过 24 小时未更新，则列入“需核查”，仍在后续检查中重新核验，不永久忽略。详情包含任务和轮次 ID、原因、首次发现和复查次数；解决后清除等待计时。计数按候选消息或失败文件计算，不是任务数量。

页面显示最后检查时间，并每 15 秒读取后台报告。读取报告不会启动修复，自动检查仍需要启动器运行及已保存的开关开启。活跃任务的新缺失目标可短暂出现，不能承诺使用期间永久为零。

“启动前自动修复历史会话”开启并保存后，启动器在启动前执行检查，并在 Codex 运行期间每次检查完成后间隔 30 分钟再次检查。每次读取已保存开关；关闭后停止后续自动检查。正在进行的事务会正常结束。检查失败记录诊断，不因消息修复失败阻止启动。

扫描范围包括当前 CODEX_HOME 的 sessions 和 archived_sessions。普通纯文本消息需要原始用户事件与 response_item 原文、轮次相互印证；目标消息需要目标事件与首轮内部上下文原文一致。恢复使用 thread_history_1.sqlite 的原生 userMessage 投影，不创建新任务、不发送新指令、不修改 rollout。

旧 inProgress 只有原始日志与原生数据库都证明后继轮次已经开始才允许补消息，不修改原有执行状态。顺序明确的目标可以补到已有问答回复前并修正首条指针，完整保留卡片中的模型提问和用户选项回复。分片归属需核对原生轮次、完成事件 ID、位置与全文，不能仅凭文件名或相同正文映射。原生轮次缺失时，仅在任务归属可信、完整开始/结束事件及首条消息身份均确定时补建历史轮次投影；不推进原生投影游标。

已有不同消息、混合附件、无法确认位置、未知数据库格式和正在变化的文件不会被猜测恢复。该工具不能恢复从未保存或已彻底删除的原文，也不保证修复所有形式的历史损坏。供应商和任务目录问题继续使用“修复历史会话”。

即使原生轮次已经存在，补入或重新连接首条用户消息也必须确认原始首条身份。首条包含不支持的附件时，后续纯文字不能取代它；悬空指针只能连接同一原生消息 ID。位置冲突按整个任务核验，与原生数据库唯一索引一致，冲突项进入核查，不阻止其他安全项修复。

普通消息的独立用户事件与完成事件按记录顺序逐个核验、一次使用；相同正文不代表同一次发送。目标按目标身份及创建时间区分，自动续执行沿用同目标，同文新目标保留独立记录。尾行 JSON 不完整时不缓存成功结果：先等待后续写入，持续未完成或超过 24 小时未更新则明确需核查。

同一响应区间出现多个完成事件时，无法唯一确认原生消息身份，仅该候选进入核查；同文件其他有独立证据的消息继续核验。重复文本的用户事件数量不匹配时，不猜测事件属于哪次发送，但仍保留已由唯一原生完成事件确认的候选。文件混入其他任务、JSON 损坏或尾行未写完时，仍暂缓整份文件。

轮次终止后到达的用户完成事件不再作为该轮次的身份或首条证据。这是保守的恢复限制，并非原生协议保证事件按序落盘的结论；若存在合法延迟持久化，可能漏修，仍需真实日志或原生协议证据核验。多个分片提供同一条消息时，身份证据必须一致；仅周边轮次、开始位置或首条辅助证据不一致时保留候选但清除冲突辅助字段，并关闭依赖该字段的首条恢复授权。冲突标记在整组分片中持续保留，第三份及更多副本不能重新填回已冲突的字段。

候选冲突同时核验原始响应位置、任务内的原生消息位置和消息 ID。即使正文相同，身份冲突也不会任意选择一个写入；缺失的辅助证据可以补全，互相矛盾的辅助证据按上述规则清除。同一目标跨分片重复出现时，优先保留已在原生索引中的分片，包括旧版本的恢复记录，避免升级后重复补入；同一目标同一位置的证据矛盾仍交给冲突核验。

性能：在每个 CODEX_HOME 内按文件路径、长度、修改时间和全文件 SHA-256 内容摘要缓存解析结果及局部核查原因；即使文件被改成相同长度并恢复旧修改时间，也不会误用旧结果。先查路径缓存与元数据：无缓存或元数据不符时，在同一遍流式读取中解析并计算摘要；元数据相同也必须读取全文验证内容，确认后复用解析结果。因此稳定缓存检查仍读取每个文件一遍，耗时取决于全部历史记录大小，不能视为零 I/O。元数据相同但摘要不符时重新解析。每次仍核对原生索引，因此原生索引重建后也能重新恢复；扫描规则版本为 v10，旧版本缓存自动失效。

发生待写入项时，在写锁前、取得 SQLite Immediate 写锁后以及提交前复核本批候选所属任务的来源文件，包括该任务已存在消息和其他分片提供的证据；其他任务的文件不被反复读取。元数据已变化时直接判为来源变化，无须再哈希；元数据相同仍核验摘要。常规冷扫描每文件读取一遍，待写任务的来源文件另作三遍复核；稳定缓存且无写入时每文件只读一遍。期间来源发生变化则放弃本次写入。

报告的普通详情最多展示 200 条，超出部分单独计数。放弃写入或回滚原因独立显示，不受详情上限或折叠影响。等待计时、复查次数和清理操作只在成功完成本轮核验后提交；来源变化导致放弃或回滚时保留原等待记录，报告不展示本轮未经确认的等待推进。缓存、最近报告和修复前的数据库备份存放在 CODEX_HOME/session-index-repair。备份可能较大，仅有待修复项且写锁前来源校验通过时创建；随后放弃或回滚也可能保留这份备份。

原生索引提交与辅助缓存使用不同数据库事务。原生修复成功后若缓存保存失败，保留真实恢复数量，并在报告中独立显示警告；不把已提交的消息误报为回滚或整体失败。下次检查仍会核对原生数据库，避免重复插入。

并发：修复锁按 CODEX_HOME 隔离，同一目录的并发修复会立即返回忙碌，不同目录可独立运行。正常返回或出错时均显式释放文件锁，避免重复或子进程继承的句柄延长锁的持有时间；同时保留与供应商同步及重启流程之间的生命周期互斥。

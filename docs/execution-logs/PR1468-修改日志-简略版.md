> 嘿 @BigPizzaV3，你给的 6 条意见我都改了，也把 VL 中转升级成生产可用。同步下每条改了啥、用了啥手段：

## Bug 1（阻塞）：`.no_proxy()` 污染共享 client

**根因**：`proxied_client()` 当初为绕 macOS 系统代理拦 127.0.0.1 测试请求，加了 `.no_proxy()`。但 reqwest 的 `.no_proxy()` 是「彻底关闭代理解析」（忽略所有代理 env），不是「只绕 127.0.0.1」。这工厂被 13 处共用，所有靠代理上网的生产请求（广告/更新/模型列表/供应商测试/上游 API）全断了。

**改法**：撤回生产 `proxied_client()` 的 `.no_proxy()`，恢复系统代理支持；测试改用 `NO_PROXY=127.0.0.1,localhost` env 只绕 localhost，公网照常走代理。
**要点**：reqwest 在 client 构建时读 env，所以 `NO_PROXY` 必须在构建 client 前设（用 `Once` 全进程设一次）。

## Bug 2（阻塞）：reasoning 剥离是死代码

**根因**：`model_supports_reasoning` / `strip_reasoning_in_place` 写了但只在测试里调，生产转发链路零调用。UI 让用户勾「模型不支持 reasoning」能存配置，但请求照带 reasoning 发上游，kimi-k2.6 这种就报 "reasoning is not supported by current model"，功能形同虚设。

**改法**：在 `upstream_request_parts` 的 Chat 分支、转换前调 `strip_reasoning_in_place`（和图片剥离同位置）。`supports_reasoning` 内部现算（不耦合 VL）。
**要点**：放这里而非 `apply_vl_with_fallback`，因为后者 VL 未启用时会提前返回，reasoning 剥离会漏执行；放转换前，避免 `apply_chat_reasoning_options` 重新注入 `thinking`/`reasoning_effort`。只覆盖 Chat 路径--Responses 透传不剥离（已知局限，text-only 模型在 Responses 下仍可能报错，用户已接受）。顺带清了同为死代码的 `strip_input_images_in_place`（按「Responses 不剥离图片」决策无生产用途）。

## Bug 3 + Bug 6（阻塞/改进）：UTF-8 截断 panic + 日志泄露正文

**根因**：VL 描述日志里 `description_preview: &description[..description.len().min(200)]` 两个问题--(1) 字节截断，中文 3 字节/字，200 落在汉字中间 → `panic: byte index 200 is not a char boundary`（中文场景几乎必现）；(2) 记录描述正文，可能含截图里的密钥/PII/代码，写进 diagnostic_log 落盘。

**改法**：直接删 `description_preview`，日志只记元数据（`description_len`/`description_chars`/vlModel/状态）。
**要点**：一石二鸟--删 preview 即无截断（Bug 3 panic 消失），又不记正文（Bug 6 泄露解决）。Bug 6 吸收 Bug 3，无需单独 char-safe 截断 preview。

## Bug 5（改进）：VL endpoint 裸拼路径

**根因**：VL 调用的 endpoint 用 `format!("{}/chat/completions", base_url)` 裸拼，没复用已有的 `chat_completions_url()` / `responses_url()`（它们处理 `/v1` 补全、`/v1/v1` 去重、`#` 跳过、origin-only 判断）。结果裸域名缺 `/v1`、完整 endpoint 重复拼，VL 调用失败。

**改法**：复用现有 helper，一行换掉。

## Bug 4（改进）：VL 串行 + 无缓存 + 无并发 + 无重试 + 无入口

这块改动最大，按 spec 详细说下。

**根因**：VL 中转在生产里基本不可用--

- **串行**：逐图 await，10 张图 × 30s = 最坏 300s 请求卡死；
- **无缓存**：failover 重跑、后续轮次重发历史图都重复调 VL，浪费费用；
- **无总超时**：单次 30s × 10 = 300s；
- **无重试**：瞬时失败直接降级 strip；
- **无入口**：缓存后无法针对同一图追问新信息（拿不到旧描述没覆盖的元素）。

**改法**（架proxy 驱动两层）：

1. **抽 `vision.rs` 模块**：VL 逻辑从 `protocol_proxy.rs` 独立，可单独测试维护，`protocol_proxy.rs` 不再膨胀。
2. **并发**：`Semaphore(5)` + `JoinSet`（tokio 自带，零新依赖），最多 5 个 VL 调用同时飞。
3. **批次（多图一调用）**：5 张图/次 API 调用（一个 messages 放 5 个 image_url + 1 个文本 prompt），省调用次数和费用；响应按 `[[图片K]]` 标注拆分回填。
4. **两层缓存**（核心，解决「无缓存 + 无入口」）：
   - **Tier 1（历史图）**：URL key + 全面描述 prompt（**不含问题**）。图从「最新」变「历史」后每轮命中，question-invariant → URL 缓存稳定。省调用大头。
   - **Tier 2（最新/重发图）**：(URL, 问题) key + 全面+侧重 prompt（**含问题**）。最新消息里的图用此层；重发图 + 新问题 = **入口**，触发新调用拿新信息。
   - **检测**：最新 user 消息里的图 + 非空问题 → Tier 2；其余（历史图 / 无问题最新图）→ Tier 1。
   - **为什么两层而非单层 (URL,Q)**：单层 (URL,Q) 对所有图 → 每个新问题所有历史图都重调（贵，N 图 × M 问题）；两层 → 历史图 URL 缓存（便宜），只有最新图随问题重调（入口）。用历史 URL 缓存换便宜，代价是最新/历史检测复杂度。
   - 500 条 / 24h TTL / 淘汰最旧；`DefaultHasher`（u64，std，比 SHA256 快，缓存 key 不需密码学强度）。
5. **双层超时**：per-batch `35+10n` 秒（单张 45s、5 图 85s）；总 180s 硬截断（`tokio::time::timeout`），超时降级 strip 不阻断用户。
6. **混合重试**：批量 2 次（治瞬时故障：网络/429/5xx）→ 失败拆单张 1 次（不折腾慢图）。指数退避 3/6s + 抖动（用 `DefaultHasher` 做 jitter，免 rand 依赖）。坏图自己重试自己的，最后只丢坏图，不拖累好图。
7. **两个 VL prompt**（关键：Tier 1 不含问题，Tier 2 含问题）：
   - Tier 1（历史，无问题）：`请详细描述这张图片，涵盖所有视觉信息：文字（逐字 OCR）、UI 元素、颜色、形状、布局结构、错误信息等。请用中文回复。`
   - Tier 2（最新，含问题）：Tier 1 + `用户当前问题：{question}\n在全面描述基础上，对与上述问题相关的内容做更详细说明。`
   - 「涵盖所有视觉信息」→ 不漏；「对问题相关处加深」→ 侧重深度。不发多轮历史给 VLM（底座模型自持完整对话上下文）。
8. **入口机制**：用户重发图 + 问新问题 → 图成「最新」→ Tier 2 新调用 → 新侧重描述（旧 comprehensive 没覆盖的元素）。天然入口，无需额外机制。重复问题命中缓存；新问题新调用。
9. **廉价兜底截断**：描述 >2000 字符 char-safe 截断（`chars().take(2000).collect()`，避免重蹈 Bug 3 字节截断 panic 覆辙）。不做完整溢出保护（主模型服务端 tokenizer 自动把 VL 描述计入上下文，正常自管）。

**好处**：快（并发 + 批次，300s → 180s 内）；省（两层缓存，5 图 × 10 轮 ~50 调用 → ~10 调用，省 ~80%）；鲁棒（重试 + 坏图隔离，一张坏图不拖垮整批）；入口（重发图能追问新信息）；模块化（`vision.rs` 独立可测）。

**坏处**：入口需重发图（文本追问不触发重查，历史图用缓存 comprehensive，若没覆盖追问点基座答不出；tool-call 架构能解决但留作未来 PR）；两层复杂度（两层缓存 + 两 prompt + 检测，比单层复杂）；不做后台静默补齐（首对话多历史图仍同步处理，180s 内）；不做溢出动态保护（极端场景多图+超长历史+小上下文可能溢出，边缘接受）。

## 补充修改（review 后追加，2 commit）

后来实测又踩一坑：VL 超时降级 strip 后基座模型拿不到图却**胡编**（用户被误导）。排查发现是**日志盲区 + strip 静默**两问题，补了两处：

### 1. 埋点取证（治日志盲区）

- `vl_call`：每次 VL HTTP 调用记 `status`(ok/timeout/http_error/send_error/...)/`duration_ms`/`error`——之前 VL 调用错误被静默吞，根本看不到卡在哪。
- `vl_strip`：strip 时记 `reason`(total_timeout/inner_error/vl_failed/vl_disabled/over_limit)——之前 strip 和成功描述都只记 `vl_preprocess_ok`，分不清。

### 2. 全部 strip 路径注入「看不到图」提示（治胡说）

VL 失败/超时/未开/超限 strip 图片时，往 body 的 `input` 注入 `role:system` 系统提示（**不传日志**，是固定模板系统消息：N 张图 + 原因 +「你无法看到，请如实告知用户，不要猜测或编造」）。Chat 路径转 system 消息、Responses 透传都支持。

| 路径 | 触发                           | 注入原因               | agent 接收状态                                         | 回复效果                       |
| ---- | ------------------------------ | ---------------------- | ------------------------------------------------------ | ------------------------------ |
| A    | VL 没开 + 纯文本模型 + Chat    | 未启用视觉模型中转     | system 提示：N 张图 + 原因 +「看不到，请告知，别瞎编」 | 回「看不了你的图（未开 VL）」  |
| B    | >10 张超限                     | 超出单次处理上限(10张) | 同上（与 VL 失败合并一条）                             | 回「图太多，N 张超限没处理」   |
| C    | 窗口外历史图                   | 不注入                 | 无提示，历史图静默消失                                 | 正常答（本就不期待历史图）     |
| D    | 坏图隔离（VL 单张重试 1 次败） | 视觉模型调用失败       | system 提示：N 张图 + 原因                             | 回「看不了你的图（VL 失败）」  |
| E    | 180s 总超时                    | VL 总超时              | 同上                                                   | 回「看不了你的图（超时）」     |
| F    | VL 内部错误                    | VL 内部错误            | 同上                                                   | 回「看不了你的图（内部错误）」 |

> 修复前 A/B 没注入 -> 模型不知道有图 -> 当纯文本答 -> 胡编图片内容（实测踩的坑）。C 不注入：历史图本就不该见、无误导风险、且可能很多很吵。

新增 3 测试（strip 注入各路径），**97 集成测试全绿**。

### 3. 文本追问图片的防御提示（防追问时模型胡说）

发图+问题（轮 1）-> 模型准确回答后，纯文本追问（轮 2+）时**不走 VL 调用**（Tier 1 缓存命中 + comprehensive 描述）。此时注入强化提示告知模型「优先从已有描述回答；若描述没覆盖追问细节，必须告知用户重发图片+问题，绝对不要猜测或编造」。

**触发条件**：最新消息无图 + 窗口内有历史图（第二轮及以后文本追问）。

**注入原因**：`用户之前发送了 N 张图片，描述已在上面。⚠️ 如果描述中没有明确覆盖的细节，必须如实告知用户需要重新发送图片并附上问题。绝对不要猜测或编造图片中未描述的细节。`

**回复效果**：大多数追问从 comprehensive 描述能直接答 ✅；极少数细节追问模型会说「请重发图+问题」✅（不胡说）；不走 VL 调用不浪费 ❌ 不浪费 ✅（缓存命中 0 调用）。

**缺陷**：proxy 侧无法判断「追问是否关于图片」，只能所有追问都注入提示。tool-call 架构（模型自己判断要不要调 VL）是正解，留作未来 PR。

新增 1 测试（追问注入），**97 集成测试全绿**（+1 方案 3 测试）。

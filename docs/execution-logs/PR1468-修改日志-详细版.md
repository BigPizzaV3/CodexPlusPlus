## 二、技术细节（按 bug）

### Bug 1（阻塞）：`.no_proxy()` 污染共享 client
- **问题**：`proxied_client()` 加了 `.no_proxy()`，被 13 处共用。reqwest 的 `.no_proxy()` 是「彻底关闭代理解析」（忽略所有 env），不是「只绕 127.0.0.1」。影响所有靠代理上网的生产请求。
- **修复**（`http_client.rs`）：撤回 `.no_proxy()`，恢复 `reqwest::Client::builder().user_agent(ua).build()`。
- **测试**（`tests/protocol_proxy.rs`）：`ensure_no_proxy_for_localhost()` 用 `Once` 全进程设 `NO_PROXY=127.0.0.1,localhost`（reqwest 构建时读 env）；`proxied_client_respects_http_proxy_after_no_proxy_revert` 设 `HTTP_PROXY` 指向代理 mock，验证 proxied_client 把 `.invalid` 请求转发给代理（区分性：若仍带 `.no_proxy()` 则 HTTP_PROXY 被忽略，代理收不到）。
- **并行安全**：先设 `NO_PROXY` 再设 `HTTP_PROXY`，并发 localhost 测试始终被 NO_PROXY 绕过。

### Bug 2（阻塞）：reasoning 剥离是死代码 + 清死代码
- **问题**：`model_supports_reasoning`/`strip_reasoning_in_place` 只在测试调用，生产转发链路零调用。不支持 reasoning 的模型（kimi-k2.6）照带 reasoning 发上游报错。`strip_input_images_in_place` 同为死代码（Responses 不剥离图片决策）。
- **修复**（`protocol_proxy.rs` `upstream_request_parts` Chat 分支）：转换前调 `strip_reasoning_in_place(&mut body, supports_reasoning)`，`supports_reasoning = model_supports_reasoning(relay, &model)`（默认 true 不误伤）。放在转换前，避免 `apply_chat_reasoning_options` 重新注入 `thinking`/`reasoning_effort`。Responses 透传不剥离（已知局限，用户接受）。
- **清理**：删 `strip_input_images_in_place` + 5 个相关测试。
- **测试**：`chat_path_strips_reasoning_when_model_unsupported`（kimi map false -> 无 thinking）、`chat_path_preserves_reasoning_when_supported`（map true -> 有 thinking）、`responses_path_preserves_reasoning_passthrough`（Responses 保留 reasoning）。

### Bug 3 + Bug 6（合并，阻塞/改进）：UTF-8 截断 panic + 日志泄露正文
- **问题**：`description_preview: &description[..description.len().min(200)]` 字节截断，中文 3 字节/字，200 落在汉字中间 -> `panic: byte index 200 is not a char boundary`；且记录描述正文可能泄露截图密钥/PII。
- **修复**（`vision.rs` vl_described 日志）：删 `description_preview`，改记 `description_len`/`description_chars` 元数据。删 preview 同时解决两者（Bug 6 吸收 Bug 3）。
- **测试**：`vl_log_does_not_panic_on_chinese_description_and_omits_body`（201 中文字符不 panic + 日志重定向到临时文件，用唯一 vlModel 定位本测试行，断言日志不含正文标记 + 元数据值正确 315 字节/115 字符）。

### Bug 4（改进）：VL 串行 + 无缓存 + 无并发 + 无重试 + 无入口

#### 4.1 抽 `vision.rs` 模块
- 纯移动（行为不变）：2 常量 + 7 函数从 `protocol_proxy.rs` 移到 `vision.rs`，公开 API 签名不变。`protocol_proxy.rs:531` 改 `crate::vision::apply_vl_with_fallback`。

#### 4.4 两层缓存 + 检测 + 4.8 两 prompt + 入口
- **Tier 1（历史图）**：`url_hash(url)` key + `TIER1_PROMPT`（全面描述，不含问题）。question-invariant -> URL 缓存稳定。
- **Tier 2（最新/重发图）**：`url_question_hash(url, question)` key + `tier2_prompt(question)`（全面 + 侧重，含问题）。
- **检测**（`is_latest_message_image`）：最新 user 消息里的图 + **非空问题** -> Tier 2；其余（历史图 / 无问题最新图）-> Tier 1。无问题的最新图归 Tier 1（无入口语义）。
- **入口**：重发图 + 新问题 -> 图成「最新」-> Tier 2 新 key -> 新调用（旧 comprehensive 没覆盖的元素）；重复问题命中。
- **淘汰**：`cache_put` 满 500 时 `min_by_key` 淘汰最旧；`cache_get` 检查 24h TTL，过期剔除。
- **测试隔离**：`vl_test_isolate()`（`VL_TEST_LOCK` 串行化 VL 测试 + **先持锁再清缓存**--临界区内清缓存，避免并行陈旧命中死等）。`cache_clear` 以 `#[doc(hidden)] pub` 暴露（同 `set_diagnostic_log_path_for_tests` 模式）。
- **测试**：`tier1_history_image_cached_by_url_no_recall`（同图二次 1 调用）、`tier2_resend_new_question_triggers_new_call`（Q1/Q2/Q1 -> 2 调用）、`tier1_prompt_has_no_question`、`tier2_prompt_includes_question`。

#### 4.2 并发 + 4.3 批次
- **并发**：`VL_SEMAPHORE: LazyLock<Semaphore>` = `Semaphore::new(5)`；`JoinSet` 并发跑各批。
- **批次**：`BATCH_SIZE=5`，同 tier 共享 prompt 故可同批。`call_vlm_batch` 构造多图 body（ChatCompletions: content 含 5 个 image_url；Responses: input 含 5 个 input_image）+ `[[图片K]]` 标注指令。
- **1 张图保持单图请求体格式**（`build_vl_batch_body` urls.len()==1 不加标注），保留单图测试断言。
- **拆分**：`parse_batch_descriptions(text, n)` 按 `[[图片K]]` 拆 n 段；任一标注缺失返回 None -> 调用方回退单张。
- **四阶段 analyze**：Phase1 收集（缓存命中即替换/超限标记/未命中收集为 VlTask）-> Phase2 分批并发 -> Phase3 join 回填（批次失败回退单张）-> Phase4 清理空对象。
- **测试**：`vl_batches_multiple_images_per_call`（5 图 1 调用 + 5 描述拆分）、`vl_processes_images_concurrently_faster_than_serial`（200ms×5 < 800ms）。

#### 4.6 混合重试 + 坏图隔离
- `call_vlm_batch` 包重试 loop：`BATCH_MAX_ATTEMPTS=2`（批量）、`SINGLE_MAX_ATTEMPTS=1`（单张回退，慢是稳定行为不折腾）。
- `backoff_delay(attempt, salt)`：`3.0 * 2^(attempt-1)`（3/6/12s）+ `DefaultHasher` 抖动（±20%，免 rand）。
- 批量重试仍失败 -> 拆单张逐个重试 -> 好图成功坏图 strip（描述为空 -> 标记 {} -> Phase4 清理）。
- **契约变更**（对齐 Bug 4.6）：`analyze` 不再返回 Err，单图失败 strip 该图返回 Ok（坏图隔离，不拖累整批）。更新 2 个旧契约测试。
- **测试**：`vl_batch_retries_on_transient_failure`（前 1 次 500 + 第 2 次 200 = 2 调用）、`vl_isolates_bad_image_via_single_fallback`（2 图含 1 坏，好图描述坏图 strip，6 调用）。

#### 4.5 双层超时 + 4.7 char-safe 截断
- **per-batch**：`per_batch_timeout(n) = 35 + 10n` 秒（单张 45s、5 图 85s；reqwest `.timeout`，替代固定 `VL_SINGLE_TIMEOUT`）。
- **总超时**：`VL_TOTAL_TIMEOUT=180s`，`analyze_images_with_vl` 包 `tokio::time::timeout`；超时/内部错误 -> `strip_all_input_images` 降级（同时清理超限空对象，避免残留畸形 part）+ 返回 Ok。
- **截断**：`truncate_char_safe(s, 2000) = s.chars().take(2000).collect()`，在 `cache_put` + 回填前。
- **测试钩子**：`set_vl_total_timeout_for_tests(Some(2s))` 覆盖生产 180s（测试快速验证降级）。
- **测试**：`vl_total_timeout_degrades_to_strip`（hang mock ~2s 降级 strip）、`vl_description_truncated_char_safe`（5000 字符 -> 2000）。

### Bug 5（改进）：VL endpoint 裸拼路径

## 七、补充修改（review 后追加，2 commit：`6c2b1b5` + `8e8211c`）

实测发现 VL 超时降级 strip 后基座模型拿不到图却胡编（用户被误导）。排查出**日志盲区 + strip 静默**两问题，补两处。

### 7.1 埋点取证（systematic-debugging Phase 1，治日志盲区）

- **`vl_call`**（`vision.rs` `call_vlm_batch_once`）：每次 VL HTTP 调用记 `status`/`duration_ms`/`http_code`/`error`。`status` 取值：`ok`/`timeout`/`http_error`/`send_error`/`json_error`/`no_text`/`parse_error`。此前 VL 调用错误被 Phase 3 `match` 静默吞掉，无法定位超时根因（看不出是挂起/报错/慢）。
- **`vl_strip`**：strip 时记 `reason`：
  - `total_timeout` / `inner_error`（`vision.rs` `analyze_images_with_vl` wrapper）
  - `vl_failed`（`analyze_images_with_vl_inner` Phase 3 单图失败）
  - `vl_disabled`（`protocol_proxy.rs` `upstream_request_parts` Chat 分支，路径 A）
  - `over_limit`（Phase 1 超限，路径 B）
  - 此前 strip 与 `vl_described` 成功都只记 `vl_preprocess_ok`，不可区分。

### 7.2 strip 注入「看不到图」系统提示（防御纵深，治胡说）

VL 失败/超时/未开/超限 strip 图片时，往 body `input` 数组注入 `role:system` 系统消息（固定模板：`用户发送了 N 张图片...（原因）...你无法看到这些图片...请如实告知用户，不要猜测或编造`）。**不传日志**，是 body 内系统消息。Chat 路径 `responses_role_to_chat_role` 映射 system -> system、Responses 透传均支持。

**6 条 strip 路径覆盖（含 1 条不注入）：**

| 路径 | 触发 | 注入原因 | agent 接收状态 | 回复效果 |
|------|------|---------|---------------|---------|
| A | VL 没开 + 纯文本模型 + Chat 协议 | `未启用视觉模型中转` | system 提示（N 张 + 原因 +「看不到，请告知，别瞎编」） | 回「看不了你的图（未开 VL）」 |
| B | >10 张超限 | `超出单次处理上限(10张)` | 同上（与 `vl_failed` 合并一条） | 回「图太多，N 张超限没处理」 |
| C | 窗口外历史图（context_window 外） | 不注入 | 无提示，历史图静默消失 | 正常答（本就不期待历史图，无误导） |
| D | 坏图隔离（VL 单张重试 1 次败） | `视觉模型调用失败` | system 提示（N 张 + 原因） | 回「看不了你的图（VL 失败）」 |
| E | 180s 总超时 | `VL 总超时` | 同上 | 回「看不了你的图（超时）」 |
| F | VL 内部错误 | `VL 内部错误` | 同上 | 回「看不了你的图（内部错误）」 |

**实现位置**：
- 路径 A：`protocol_proxy.rs` `upstream_request_parts` Chat 分支，`supports_image=false` 时调 `vision::inject_strip_note_if_images`（pub helper：计数 input_image + 注入 system 消息），转换 strip 前注入；记 `vl_strip(vl_disabled)`。
- 路径 B：`vision.rs` Phase 1 `over_limit_count` 计数（`vl_count > VL_IMAGE_LIMIT` 时 ++ + 记 `vl_strip(over_limit)`），Phase 4 后与 `vl_failed_count` 合并注入一条（`reason` 按两者组合：`超出上限` / `VL 调用失败` / `N 张超上限、M 张 VL 失败`）。
- 路径 D/E/F：`vision.rs` Phase 3（`vl_failed`）+ wrapper（`total_timeout`/`inner_error`，`strip_all_input_images` 后注入）。
- 路径 C：不注入（历史图、无误导风险、可能很吵）。

**修复前**：A/B 没注入 -> 模型不知道有图 -> 当纯文本答 -> 胡编图片内容（实测踩坑，2 图超时 strip 后基座胡说）。

### 7.4 方案 3：文本追问时注入防御提示（治追问胡编）

**问题**：发图+问题（轮1）-> 模型准确回答后，纯文本追问（轮2+）不走 VL 调用（Tier 1 缓存命中 + comprehensive 描述）。若 comprehensive 描述没覆盖追问细节，模型可能根据不充分的信息胡编。

**根因**：`is_latest_message_image(input, idx) == false`（图在历史消息），走 Tier 1 `url_hash`（无问题侧重）。proxy 侧无法语义判断「追问是否关于图片」—— 这是 tool-call 架构才解的题。

**方案**：不走 VL 重调（避免浪费），改为注入强化提示。
- **检测**：`is_followup_query = !user_text.is_empty() && !latest_user_message_has_image(input) && 窗口内有图`（Phase 0 捕获，在替换图片为 text 前）。
- **注入位置**：`vision.rs` `analyze_images_with_vl_inner` Phase 4，`total_stripped == 0 && is_followup_query` 时调 `inject_followup_note`。
- **注入内容**：
  ```
  [系统提示：用户之前发送了 N 张图片，这些图片的文字描述已在上面（# 图片内容描述）。
  请优先从这些描述回答用户的问题。
  ⚠️ 重要限制：如果你认为用户追问的是描述中没有明确覆盖的细节，必须如实告知用户
  「你的问题需要我重新查看原始图片，请重新发送图片并附上问题」。
  绝对不要猜测或编造图片中未描述的细节。]
  ```
- **触发路径**：第二轮及以后纯文本追问，历史图被 Tier 1 缓存命中 → 替换为 cached description → Phase 4 注入提示。

**回复效果**：大多数追问从 comprehensive 描述直接答 ✅；极少数细节追问模型说「请重发」✅；0 浪费（缓存命中）。不可靠点：模型可能不遵从提示、comprehensive 可能遗漏细节。

**缺陷**：proxy 侧无法判断「追问是否关于图片」，只能所有追问都注入提示（浪费是工具调用决策，非 proxy 启发式能解）。tool-call 架构（基座模型自主调 VL，带当前问题）是正解，但需多轮协议改造，留作未来独立 PR。

**新增辅助函数**：
- `latest_user_message_has_image(input)`：判最新 user 消息是否含 `input_image`（`vision.rs:151`）。
- `inject_followup_note(input, n)`：注入强化提示（`vision.rs:540`）。
- `inject_strip_note_if_images(body, reason)`：pub 供 `protocol_proxy.rs` 转换层 strip 路径调用（`vision.rs:554`）。

**测试**：`vl_strip_injects_cannot_see_image_note_on_timeout`（路径 E 注入）、`vl_disabled_chat_path_strips_image_and_injects_note`（路径 A 注入）、`vl_over_limit_strips_and_injects_note`（路径 B 注入）。tier1 测试断言改为按 `role==user` 定位描述消息（避免被 system 提示索引干扰）。

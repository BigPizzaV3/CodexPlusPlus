# 本机结构化用量接口

`/usage/history` 默认关闭，需开启 `usageHistoryEnabled`。首次查询才创建索引，
没有查询约一分钟后释放；关闭设置等待正在进行的扫描结束。请求不能指定文件路径。
原始会话、配置和登录信息均不修改，不发起模型请求。

## 查询与响应

支持 `period`、`from`、`to`、`model`、`sessionId`、`turnId`、`search`。
`startAt` / `endAt` 为成对的毫秒时间戳，使用 `[startAt,endAt)` 半开区间。
`scopeSessionId` 仅统计明确的子智能体后代，普通 fork 不算子智能体。
`includeSessionCursors` 和 `includeActivity` 必须显式开启；
`activityPage` 每页至多 512 条，`activityRevision` 可避免重复传输未变活动。

响应为 `accountingVersion:2` 的结构化 `days`，包含模型、供应商和
`main/subagent/unknown` 分类、会话别名及父子关系、完整性和累计水位。
本层替换基础读取器响应，不提供旧版的费用、价格和挂件展示字段；
上游鲸鱼挂件仍使用独立的读取器、设置和路由。
调用方必须按版本消费，不能把累计水位当作消费增量。

同一会话所有分段参与汇总；共享观测去重，独立计数流分别计量。
同名的普通 `.jsonl` 副本须逐字节核对已提交前缀，才共用用量游标；
副本变更时重新核对，已验证的较短副本不能接续超出其长度的游标。
分页 fork 或 revert 按明确引用的物理 rollout 前缀恢复累计基线，不把前缀再次计入。
缺少基线、计数冲突和损坏时间保持 `partial`，不把历史累计计入当前日期。
缓存输入是输入的子集，总量为输入加输出；`cachedKnown` /
`reasoningKnown` 为 false 时不能把缺失计数当作精确的零。
`accountingFingerprint` 和 `membershipFingerprint` 绑定事件与计数，
不能单独证明扫描完整或分类正确。
默认返回可从逐笔记录核验的指纹；日期行的 `fingerprintCoverage` 为 `events`。
若仅有日汇总，或原会话回读无法核对成员，则为 `unavailable`，并省略这两个字段。
只展示用量的调用方可传 `includeFingerprints: false`，避免为完整日期重新读取逐笔记录。
分组的 `providerName` 来自同一响应的 `providerNames`，查不到名称时为 `null`。
未按会话、轮次、模型或关键字筛选的查询，可用 `includeLegacySummary: true`
读取本机已有的旧版日摘要。`legacyDays` 是独立的部分覆盖结果，不计入原生 `days`，
也不提供逐笔指纹或分时明细。
分段基线修正会改变受影响历史范围的计数和指纹；响应格式、计量单位不变，
因此仍返回 `accountingVersion:2`。调用方应按新指纹替换旧结果，而非叠加。

工具活动只保留已完成调用的成功、失败、退出状态及技能分类元数据，
不返回命令、真实路径、正文和完整调用参数。默认不返回活动。

`/usage/executions` 的普通工具列表与名称搜索覆盖最近 7 天。更早的普通工具
仍按调用身份和时间计入范围总数，但不返回列表项；技能和 MCP 名称及时间轴
保留到逐笔明细边界。`summary.matched` 只计入能列出的匹配项，不改变范围总数。
`/usage/execution-detail` 通过最近 24 小时的定位从原会话按需读取输入输出；
输入输出正文不存入索引。

## 资源与生命周期

支持活动和归档目录中的 `.jsonl` / `.jsonl.zst`。持久索引的逐笔明细默认保留
最近 60 个本地日期（含当天）；到期后保留日汇总，有原会话时可按需回读。
`scan.retentionDays` 为保留设置，`scan.preciseFrom` 为已提交的逐笔保留边界
（尚未提交时为 `null`）。保留期不等于覆盖范围，查询完整性以 `coverage` 为准。
通过 `usageHistoryPreciseDays` 可调整精确保留期；延长后不自动恢复已汇总的明细。
索引工作预算 `usageHistoryStorageMiB` 默认 2048 MiB，包含主库、WAL 和辅助文件，
不包含独立的归属证明缓存和旧索引。空间不足时按日期先回收已到期的工具日汇总；
受影响的工具范围返回 `coverage.reason: "storage-pruned"`。
长读取占用 WAL 时暂停写入，不删除记录。空间仍不足时保留最后已提交快照，
`scan.storageBlocked` 提示写入受限；释放空间或提高预算后从原游标续读。
`scan.sourceIssues` 汇总来源发现和摄取问题，不等于旧扫描器的坏记录条数。
不提供旧扫描器的耗时、读取字节和已索引文件计数。
文件状态保留预算 64 MiB，普通扫描每批输入和解压预算各 4 MiB。行缓冲区使用 1 MiB，更大的终态回执和原生计数按字段读取，并保留原始字节位置。
当排队的变更均为已登记普通文件的追加，且总追加量在共享预算内时，同一轮可连续提交多批，读到已观察的文件末尾后再判断归属。
计量记录需要联合核对时，先尝试增量处理或整理旧观测。关联组仍超出共享工作预算时，保留当前批次，下一轮按整组实际大小重算。明细、汇总和游标在同一事务中提交。即使文件末尾还有半行，前面的完整记录也能先入账。
预算是索引准入估算，不是整个进程的内存上限。
已辨认的无关长行直接跳过。可能含计量信息的超长行到达结尾后再提取字段，普通日志按原文件范围重读，压缩日志在扫描期间使用自动回收的临时文件。损坏或无法还原的相关行标记不完整，扫描继续处理后续记录。
旧检查点若已读过 1 MiB 且存在超长跳行可能造成的来源问题，升级后按原文件重读，核对完成后在同一事务中替换原结果。
查询驱动扫描，每十秒最多刷新一次；空闲计时器只释放内存，不扫描会话。
`scan.processing=true` 时可能仍返回上一快照，应等待本轮刷新完成。

派生证据与计数冲突保护保存在 Codex++ 设置目录的
`usage-history/<home-id>/usage-provider-cache.sqlite`，不同 Codex home 分开。
原生 SQLite 日志尊重显式的 `CODEX_SQLITE_HOME`，不能退回另一实例目录。
缓存不可用时保守报告完整性，不能把缺失事件解释为零消费。

## 归属证据

事件自身明确归属优先。请求日志、实际 HTTP 完成日志必须按会话、时间、
模型和完整计数核验，双向不唯一、冲突或失败的请求保持未知。
模型命名空间与当前供应商选择都不能证明历史账单归属。
供应商身份使用稳定 ID；显示名缺失或变化不影响完整证据的归类，
没有可用名称时显示 ID。此前已持久拒绝的请求不会自动解除拒绝。
同一完成请求重读时可补入最终响应 ID 和已确认的缓存数；弱记录不覆盖已知值。
成功但缺少用量的请求保留身份。日志轮转后，它仍参与同会话的竞争判断，不能单独证明某笔用量的归属。
旧日志中未标明来源的零缓存不能建立新归类，除非最终响应标记已证明计数完整。
已经验证的旧证明仍可用于原事件，即使请求日志已经轮转；冲突时仍撤销。
不同的已知响应 ID、供应商或计数仍是冲突。补证只影响分类，不改变消费次数或 Token 数量。
完成请求的旧版 JSON 投影和回执签名保持原格式，新增观察字段单独保存。
旧版读取不到新增字段；原始计数或其他旧字段实际变化时，仍按旧版冲突规则处理。
实时通知允许完成日志晚到至多一秒，但请求必须在通知前开始；
完整计数、双向唯一性、顺序、竞争撤销和持久化重验仍保留。
归属修复不会产生新用量。

历史读取可用同一会话和回合的原生 `token_usage_record` 核对已有计数行。
原生和网关的最终响应 ID 均唯一、完整计数一致，且在普通匹配窗口内时，
使用网关的实际模型和供应商；同路由但不含用量及响应 ID 的近邻不会挡住这类补证。
被拒绝的配对候选不会用于归属；不同路由、明确的直连供应商冲突和计数不明仍按原规则处理。
原生回执本身不新增消费条目。

普通请求按通知前 30 秒回看。只有带 `finalResponseEvidence: "final-response-v1"`
的单个成功最终响应，才允许通知前最多 120 秒的延迟补认，并支持已验证的重试。
该标记由本机响应链路提供；没有标记时仍要求单次、无自动重试的请求。
内置 Chat Completions 转换也保存实际送达的最终响应 ID；完整用量经含缓存口径对齐后
可提供同一标记。缓存未知但响应 ID、实际路由与模型明确时，保存
`finalResponseEvidence: "final-response-supplier-v1"`，同时保留 `cachedTokensKnown: false`。
该供应商证据不证明缓存计数完整，不能替代计数匹配所需的完整用量标记。
原生回执和网关记录的终态 ID、会话、输入和输出计数一致且没有竞争归属时，
历史用量以 `supplierClassificationEvidence: "request-log-recovered-supplier-only"` 返回供应商，
不改写原生模型或任何 Token 计数。
转换失败、截断以及未验证的响应改写不产生终态证明。
通知之后的完成日志仍最多晚一秒，请求必须在通知前开始。
延迟组合、无标记记录和模型冲突仍占用竞争证据，不会因自身不符合补认条件而被忽略；
只有完整计数和双向唯一性均成立时才补认，保存的证明在重读时重新验证。

`liveReceipts` 核验整批回执。一次累计增量可以对应同一供应商、同一最终模型的多个连续请求，
请求必须按先后顺序完成，三项计数的合计必须与回执吻合。每个请求只能归属一个回执。
查询按会话和匹配时间窗读取已有请求缓存。别名、拒绝身份和保留边界来自同一只读事务，
不创建、迁移或清理数据库，也不持久化查询中新发现的冲突。
当保留边界或旧日志缺口导致证据不足时，该回执及同会话中与它竞争窗口重叠的回执保持待确认。
缓存与当前日志重复的同一请求只匹配一次，内容不一致仍拒绝。
名称变化不构成冲突；旧回执包含名称的签名只在原记录仍可核对时接受。
后台按时间片归类近期会话，额外读取完整的前后竞争范围。邻接记录参与验证但不被改写；
缺少边界证据时不会用截断的范围认定唯一归属。

设置目录中的 `usage-provider-evidence.json` 可提供版本 1 的事件绑定补证。
导入会读取完整文档并核对事件 ID、会话、时间、角色和计数。
精确上游证据可补缺失模型，用户分类不能补模型或进入实时精确证明。
来源通过 `providerSource` / `providerEvidence.sources` 保留。
导入是本地只读消费，不写原始日志；删除文件后下一轮撤销补证。

## 按需供应商采集

首次查询才运行有界采集器，开启设置或启动管理器本身不采集。
它跟随索引生命周期，空闲、关闭或切换 home 时先停止采集，再等待在途扫描结束。
同一 home 使用状态目录单写者锁；不同 home 独立保存证据。
网关请求按保留期保存。原生日志按游标分批读取，后续采集从已提交的位置继续。

采集尊重打开文件身份、轮转、缺口和配置版本；
设置或网关供应商配置变化后重新绑定，配置无效时清除旧绑定并重试。
它不发送模型请求，不保存 API Key、请求头、正文或完整端点 URL。

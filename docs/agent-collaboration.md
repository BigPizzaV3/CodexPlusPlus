# 在 Codex 中使用外部子 Agent

Codex++ 最左侧的「Agent 协作」入口提供「子 Agent 设置」。日常任务在 Codex 对话里发起，管理器负责默认 Agent、CLI 路径、模型与接入配置。

## 日常用法

1. 打开「子 Agent 设置」，启用协作及需要使用的 Agent，选择默认 Agent，保存配置。
2. 点击「一键接入并刷新」。配置只管理 `codex_plus_collaboration` 条目，并同步到 Codex++ 的托管 MCP 配置，后续切换供应商仍会保留。
3. 检查独立的运行刷新状态。存在 Codex++ 原生连接时会重载本机 MCP 配置、检查子 Agent 工具并刷新 `/mcp` 的列表缓存；刷新后的工具从下一轮消息起可用。缺少连接时，先用 Codex++ 启动或接管 Codex，再点「刷新 Codex 工具」，也可在 Codex 手动重新加载 MCP。
4. 直接向 Codex 说明任务，例如：

   - 「让 DeepSeek 实现这个功能，你负责检查结果。」
   - 「让 Claude Code 审核刚才的改动。」
   - 「把这项调查交给默认子 Agent，完成后汇总给我。」

明确点名 DeepSeek、Claude Code 或另一个 Codex 时，委派到对应 Agent；未点名时才使用默认 Agent。目标不可用时不会擅自换成其他 Agent。

Codex 获得异步任务 ID 后可以继续独立工作，再通过等待或查询工具取得终态和答案，在原对话中向用户汇报。仅提交成功不能当作执行成功。

`/mcp` 面板缓存的是全局列表，原生客户端当前会缓存 5 分钟。新聊天的 MCP 就绪不一定会更新这份列表，旧聊天也不一定自动获得新工具。因此「已接入配置」「工具已发现」「列表缓存已刷新」分开显示；刷新入口会重读本机全部 MCP 配置，仅检查本服务，不会发起聊天回合或调用模型。

如果显示「子 Agent 工具已就绪，列表待确认」，委派工具已加载；下方会说明列表检查停在哪一步。尚未打开 `/mcp` 或其查询已被回收时，没有现成列表缓存可刷新，先打开 `/mcp` 再检查即可。刷新只使用拥有本机 MCP 列表查询的缓存对象，不会创建假查询或填入推测状态。

列表查询走 Codex 的后台队列，可能超过管理器的短等待窗口。等待超时会显示「列表仍在后台刷新」，不会当作请求失败，也不会取消或重启正在进行的查询；稍后重新打开 `/mcp` 查看即可，无需重新接入。

## 子 Agent 配置

- 支持 Codex、DeepSeek Harness、Claude Code；任务实际在对应 CLI 内执行。
- 保存总开关和各 Agent 的启用状态后才能派任务。
- 默认 Agent 仅影响未明确指定目标的委派。默认目标未启用时会报错，显式点名其他已启用目标仍然可用。
- Codex、Claude Code 可选填模型；留空沿用原生 CLI 默认模型。DeepSeek 可填写 `provider/model` 模型路由，例如 `deepseek-account/deepseek-flash`；账户登录使用 `deepseek-account`，API 密钥使用 `deepseek-official`。模型名称需在对应供应商中可用，留空沿用 DSH headless 的默认路由。
- 可执行文件路径留空时自动发现，填写时必须是绝对路径。检测到文件不代表已登录或模型可用。
- DeepSeek 可选择「复用 DSH 已保存的登录与密钥」，默认关闭。开启后由 dsh 自行读取原生认证，Codex++ 只保存此开关，不读取或保存登录与密钥；此开关不会自动选择 DeepSeek 桌面当前使用的模型。
- 每个 Agent 可在「同时执行任务数」中设置并发上限（1–4，默认 1）。同一 Agent 运行中的任务数小于上限、且前面没有更早的排队任务时，新任务直接启动；达到上限后，新任务不会被拒绝，而是进入该 Agent 的队列：委派工具立即返回 `taskId`，状态为 `queued`，`progress` 说明前面还有几个任务要先结束；任一运行中的任务结束（完成、失败、取消或中断）后按提交顺序自动启动下一个。并发和排队是叠加关系：上限为 1 时与只排队、逐个执行的行为完全一致。
- 并发上限对同一 Agent 的所有任务统一生效，不区分来自哪个会话或进程：同一个 Codex 会话连续派发多个互不依赖的任务、多个会话或客户端同时派发，都共用这个上限和同一个队列。是否轮到在同一个数据库写事务里判断并认领，多个进程同时判断也不会超过上限。
- 并发执行的每个任务都有独立的 CLI 进程、原生会话和 `taskId`，`wait_task`、`get_task`、`cancel_task` 只作用于传入的那个任务。CLI 直接在各自的工作目录中修改文件，协作服务不做隔离：可能同时运行的任务应使用不同的工作目录（例如各自的 git worktree）。同一工作目录还有其他任务可能同时运行时不会拒绝，只在委派返回的 `cwdWarning` 和任务启动时的 `progress` 中提示一句。
- 每个 Agent 最多排队 8 个任务（不含正在执行的），超出时明确报错，不写入任务。排队等待的时间不计入单个任务的运行上限。取消排队中的任务会立即把它移出队列，后面的任务顺位前移；取消运行中的任务时，该任务在 CLI 停止前仍占用一个并发名额。
- 不同 Agent 之间始终可以并行，各自的并发上限互不影响。
- 新任务创建独立会话；已完成且记录了原生会话 ID 的任务可选择「继续该任务」，续聊固定原 Agent 与工作目录。
- 提示词经 stdin 传入，不通过 shell 拼接。协作服务不会读取、复制或改写各 CLI 的凭据和供应商配置。
- 任务最长运行 10 分钟；取消会停止本次启动的 CLI，Unix 同时停止其进程组。已发生的文件或外部操作不回滚。
- 任务由发起它的管理器或 MCP 进程托管；正常退出该进程会中断其尚未完成的任务，其他客户端进程的任务不受影响。
- 排队任务同样由提交它的进程托管并定期续租。该进程正常退出时，其排队任务立即标记为 `failed`；进程崩溃或失联时，约 1 分钟租约过期后同样标记为 `failed`；电脑睡眠或进程卡顿导致租约过期时，只要提交它的进程仍在（以该进程持有的文件锁判断），任务继续排队，不会被误判失联。排在队首的任务每秒检查一次是否轮到，其余约 5 秒检查一次，本进程的任务结束时立即重新检查。错误信息会说明任务未启动、没有执行任何操作，可以放心重新提交；失联进程的排队任务不会一直挡住后面的任务，也不会卡在 `queued`。不同进程提交到同一 Agent 的任务共用同一个队列和并发上限，按提交顺序启动。
- 中断、失败或通信结果不确定时不会自动重试；请先检查结果。

DSH headless 默认使用环境凭据。若已在 DeepSeek Harness 中登录或保存密钥，可在子 Agent 设置中开启「复用 DSH 已保存的登录与密钥」，并明确选择与认证方式匹配的模型路由。协作服务通过本次任务专用的 `--patch` 文件启用 DSH 原生保存认证能力及可选的模型路由，不修改 DSH 的持久配置。只有显式选择 `deepseek-account` 路由时才启用账户服务，API 密钥路由不初始化账户登录。生成的无凭据 JSON 保存在协作状态目录的 `agent-collaboration-overlays/<taskId>.json`，用于排查本次参数。

复用认证不会导入 desktop profile 的其他设置。自定义账户服务地址需先在 DSH headless profile 中配置正确；思考强度等参数沿用 headless 配置。更改模型路由用于新任务，继续已有原生会话时仍由 DSH 使用该会话的模型。若仍报告认证失败，请检查 DSH 原生登录是否有效以及所选模型使用的供应商路由。Codex 和 Claude Code 同样需要可用的原生登录与模型设置。

升级后若 Codex 仍连接旧版 MCP 进程，请在新版管理器中点击「一键接入并刷新」，让后续委派使用新版执行器及配置。

## 手动接入及其他客户端

「手动接入与配置导出」中保留 MCP 配置。Codex 使用 TOML 片段，Claude Code 及兼容客户端可使用 `mcpServers` JSON；DSH 按其 MCP 配置格式填写同一 command/args。只有显式点击「一键接入并刷新」才会修改 Codex 的接入配置，保存子 Agent 参数不会自动改外部客户端；单独的「刷新 Codex 工具」不写配置文件。

配置指向当前运行的 Codex++ 可执行文件，参数为：

```text
--codex-plus-agent-mcp --state-dir <Codex++ 状态目录的绝对路径>
```

该模式在 GUI 与单实例检查之前启动，只在 stdout 输出 MCP JSONL。所有客户端使用同一状态目录时共享协作开关、任务和结果。移动或删除本地构建后，需要重新生成指向有效可执行文件的配置。

工具：

| 工具 | 用途 |
| --- | --- |
| `list_agents` | 查看启用状态及 CLI 文件可用性 |
| `delegate_to_deepseek` | 用户点名 DeepSeek 时委派 |
| `delegate_to_claude_code` | 用户点名 Claude Code 时委派 |
| `delegate_to_codex` | 委派给另一个 Codex CLI |
| `delegate_task` | 可省略 `agentId`，使用默认子 Agent |
| `send_task` | 异步派发，返回 `taskId` |
| `wait_task` | 每次最多等待 30 秒，返回终态或仍在执行的状态 |
| `get_task` | 按 `taskId` 查询进度、最终答案和原生会话 ID |
| `list_tasks` | 查看最近任务及活跃任务 |
| `cancel_task` | 请求停止指定任务；排队中的任务立即取消并移出队列 |

`send_task` 参数示例：

```json
{
  "agentId": "deepseek",
  "prompt": "检查当前仓库的测试失败原因，返回证据与建议。",
  "cwd": "/absolute/path/to/project"
}
```

任务提交成功仅表示已入队；同一 Agent 运行中的任务未达并发上限时立即启动 CLI，达到上限时先排队，轮到后才启动。需要并发的多个任务请分别传入不同的 `cwd`。调用方继续独立工作，随后使用 `get_task` 查询同一个 `taskId`；只有 `completed` 表示成功。追加任务时传入 `continueTaskId`，其值为已完成的协作任务 ID，不能填任意桌面聊天 ID。

## 存储和边界

任务与配置保存在 Codex++ 状态目录下的 `agent-collaboration.sqlite3`，独立于现有 `settings.json` 与原生会话数据库。任务记录上限 1000 条，单条提示词最多 64 KiB，最终答案最多 256 KiB；超限明确报错。界面展示活跃任务及最近历史，最多 50 条。记录不会自动删除。

当前通过 MCP 把原生 CLI 作为外部子 Agent 调用，不属于 Codex 原生 `spawn_agent` 子树；不会接管已打开的其他桌面会话。MCP 会如实返回 `desktopSessionWake: false`。这些边界不影响在 Codex 对话中委派并收取结果。

后续桌面接入层应使用明确的 host/session 身份、保留原生权限和会话状态；新增协作写能力不应直接开放到现有第三方拓展路由白名单。

# 本地压缩缓存复用（实验）

在单个供应商的请求设置中启用“本地压缩缓存复用（实验）”，可尝试提高本地压缩请求的缓存命中概率。默认关闭，开关独立保存在每个供应商上。单模型路由可以在入口或实际目标供应商启用；聚合请求使用实际成员的设置。Responses API 与 Chat Completions 支持此实验，纯官方登录、聚合入口和 Anthropic Messages 不提供此开关。

用户实测表明，这种方式可以改善压缩请求的缓存命中概率，但不保证每次命中，也不保证将压缩提示放在上下文末尾不会影响摘要质量。建议结合供应商返回的缓存用量、费用和实际摘要内容判断是否保留。关闭后恢复普通本地压缩路径。

实验通过本地代理记住同一会话此前的普通请求。在识别到本地压缩、完整历史前缀匹配且隔离条件一致时，保留当前完整历史和末尾压缩提示，复用此前普通请求的工具声明，同时禁止模型调用工具。当前请求的输出限制、推理设置和其他参数保留，不会被旧请求覆盖。找不到合适请求、历史被裁剪或遇到原生远程压缩时，使用原有路径。

请求缓存仅保留在当前代理进程内，退出后清空；最多保留 16 条、合计 32 MiB，每条不超过 8 MiB，15 分钟后失效。这是代理用于构造请求的缓存，与供应商实际缓存是否仍可用是两回事。候选摘要包含工具调用、输出不完整或返回 HTTP 400/422 时，尝试原本的压缩请求；这次额外尝试可能增加等待时间和费用。限流和服务端错误沿用已有失败切换行为。

此前的“搜索历史压缩兼容（实验）”已退役，相关服务端修复已合入 sub2api。旧配置中的 `webSearchHistoryCompat` 会被忽略，不会自动开启新实验，也不再为自定义供应商主动补入搜索工具声明。上游针对官方登录路径的自动兼容处理继续保留。已保存真实 `upstreamBaseUrl` 的本地代理配置会继续使用该真实上游，避免将代理自身当作供应商。

“前缀稳定层”是独立设置，其行为与本实验分开控制。

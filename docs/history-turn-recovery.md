# 会话索引修复的前端补载阶段

在 Codex 中，有时历史搜索能找到消息，但滚动到对应时间段却看不到内容，或只显示中间工作过程，缺少最终答复、文件改动或用时。一种已确认的情况是：原始记录和历史索引仍然完整，前端已经登记了轮次，却没有加载完整消息。已有用户输入、已有部分消息，甚至连续多个非空轮次，都不代表消息分页已经完成。

此功能只处理这种前端补载缺口，不修复丢失的原始文件、损坏的索引或尚未登记的历史页。

## 入口与触发

先在管理工具或 Codex 内的增强设置中开启「历史轮次补载（实验）」。该开关默认关闭，与原有的自动索引检查开关独立；关闭时不联系原生页面、不定位内部管理器，也不执行前端补载。

开启后，沿用「会话管理 → 修复会话索引」按钮及现有自动检查流程。索引检查成功且未中止后，在后台向已经注入的 Codex 主窗口发出一次补载请求；数据库检查报告先返回，不等待最多 20 秒的前端结果。自动检查保留现有启动后的首次执行、每次检查结束后间隔 30 分钟复查及激活已有实例的流程；手动按钮不依赖自动检查开关。读取或刷新修复报告不会触发补载，不增加常驻扫描或重试任务。

只修复当前本机会话中已经登记的终态轮次，包括连续非空但分页未完成的轮次，不再要求前后有内容作为锚点。不会加载未登记的历史消息页或其他会话。没有现存页面或当前没有可安全补载的会话时跳过，不把请求留到之后打开其他会话时执行。

## 行为与边界

- 调用 Codex 原生的历史消息加载器，让其更新自身的前端状态；不伪造消息或直接修改 DOM 中的聊天正文。最终答复及文件改动来自原生消息，不通过猜测工作过程生成。
- 原生消息分页不更新轮次用时。对缺失的用时和开始、完成时间，以 `thread/turns/list` 的 `notLoaded` 模式查找轮次元数据，不请求消息正文；只有原生 ID 与终态一致时，才通过原生状态更新接口填入缺值。保留已有值（包括 0），不改轮次状态、消息、输入、分页游标或历史区段，不整体重建会话。
- 前端阶段不改写 rollout、SQLite、供应商或模型配置，不启动新轮次，不发送模型请求；原有索引修复的证据核验、备份和事务保护保持不变。
- 每次读取前后核验开关、原生忙碌状态、管理器归属及历史代际。正在生成、存在未确认提交或已有历史加载进行中时让步；关闭开关、切换会话、隐藏窗口、管理器或历史代际变化、重新注入后停止后续补载。元数据更新还要求当前窗口持有原生 owner 角色，并在更新回调中重复核验。已经发出的读取由原生加载器完成，关闭开关不能撤销已开始的原生调用。
- 先串行补齐选定轮次的消息，再查找缺失的时间信息，避免慢元数据查询阻塞正文及文件改动恢复。每次索引检查最多处理 32 个轮次，消息和元数据合计最多 128 次分页调用，其中元数据查找最多 64 页、每页 32 个轮次；超过 12 秒不再发起新读取。取消每轮四页的提前截断，只以原生 `hasLoadedOldest` 确认消息分页完成，不因用户输入或部分工作过程出现而停机。
- 触及预算仍未补齐、元数据读取不兼容或源记录没有对应时间值时，结果为部分完成，不伪造完整报告。后续再次使用原有修复入口时，非空缺页仍可继续处理；保留原生驱逐与重连边界。
- 读取失败或没有进展时结束本次请求，不安排定时重试；需要时可再次使用已有「修复会话索引」按钮。同一个请求去重，并发请求不排队，重新注入共享正在进行的读取。
- 原生结构无法识别、端口或主窗口归属不明确时安全跳过，不猜测内部接口或默认连接其他实例。内部管理器 family 的源码守卫必须唯一匹配；零匹配或多匹配都返回不可用，不读取或写入原生会话状态。
- 保留原有报告的消息恢复计数，不把前端分页读取数混入数据库修复数量。修复报告先显示 `pending`，后续原有的 15 秒报告刷新会显示 `completed`（本次范围已完成）、`partial`（仍有缺页或元数据缺值）、`unavailable`（原生接口不可用或未能确认）或 `skipped`（本次未执行），并分别列出消息页数和元数据页数。刷新只读结果，不启动补载。
- 结果独立存放在 `CODEX_HOME/session-index-repair/frontend-report.json`，只保留最近一次检查，按检查时间及请求身份防止旧请求覆盖新结果；不会改写数据库报告。遗留 `pending` 超过 30 秒显示 `unavailable / background_interrupted`。原生页面尚未注入时记录 `runtime_unavailable`；状态记录写入失败时记录 `report_write_failed` 诊断，页面可能无法显示本次前端结果。这些失败均不反转已提交的索引修复。
- 跳过或不完整原因使用不含聊天内容、会话 ID 和原生异常正文的固定代码，同步写入 `session_index_repair.frontend` 诊断：`window_hidden` 为窗口隐藏，`debug_port_unavailable` 为没有可用调试端口，`disabled_or_settings_unavailable` 为开关关闭或设置不可读，`index_repair_aborted` 为索引检查中止；`no_local_thread` / `unsupported_window` 为没有可确认的本机会话或不支持的窗口，`thread_busy` / `recovery_busy` 为原生会话或已有补载忙碌。接口不兼容使用 `native_api_unavailable` / `native_state_unavailable` / `frontend_unavailable`，超时使用 `frontend_timeout`，上下文变化使用 `context_changed`；预算、读取停滞或元数据缺值使用 `budget_exhausted` / `native_read_failed` / `incomplete`。可在条件恢复后再次点击原有修复按钮。
- 仅适配主窗口中的本机会话；远端主机、活动悬浮层和快捷聊天不在此阶段范围内。

此功能是对已确认症状的有界恢复措施，不表示已经查明最初漏加载的触发原因。2026-10-27 已按维护者要求在 Windows 真实安装测试通过，人工反馈确认「默认关闭 → 开启 → 点击修复 → 数据库报告先返回 → 后台补载生效及状态更新」。同机 Codex 客户端版本为 `26.1021.3705.0`；对已安装客户端的 `app-initial-438d1df57f70.js` 静态复核，内部管理器源码守卫与对应导出均恰好命中一次。真人验收结论来自实际安装使用反馈，源码匹配次数来自独立静态检查，不以 mock 或隔离启动代替真人验收。
